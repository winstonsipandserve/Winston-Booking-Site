## Project Identity

**Winston Sip and Serve** — a booking platform + admin panel for a sports facility offering tennis, pickleball, and golf simulator bays.

- **Current build scope**: Customer-facing booking flow, and an admin panel for staff to manage resources, bookings, and (once defined) memberships.
- **Not in current scope**: A POS system is planned as a future extension of this same platform (see "Scope & Future Extension" below) — do not build POS features now.
- **Single venue**: No multi-location support needed at this time.

- **Repo**: `https://github.com/winstonsipandserve/Winston-Booking-Site.git`
- **Local**: `C:\Projects\winston-booking-website`
- **Branches**:
  - `main` — production, auto-deploys to Vercel Production
  - `staging` — pre-production testing
  - `dev` — day-to-day development work

## Architecture Decisions

These are locked in. Don't deviate without discussing first.

- **Resource model**: `ResourceType` contains individual `Resource` records (specific court/bay) — one unified system, not per-sport tables. There are 5 resource types: `tennis-court`, `pickleball-court`, `tennis-sim`, `pickleball-sim`, `golf-sim`. Current inventory: 1 tennis court, 3 pickleball courts, 1 tennis simulator, 2 pickleball simulators, 2 golf simulators.
- **Home stat banner is a static snapshot, not live-queried** — a hardcoded copy of the inventory list above. If inventory changes, update both this doc and `StatsBar.tsx`'s `TOTAL_RESOURCES`/`SPORT_COUNT` constants.
- **Double-booking prevention**: Enforced at the database level via a PostgreSQL exclusion constraint on overlapping `tsrange` (using `btree_gist`) combined with a pending-hold-and-expire flow — not an application-level check, no admin bypass. Prisma can't express `EXCLUDE USING gist` natively, so the constraint is raw SQL, master copy at `prisma/manual-sql/booking-exclusion-constraint.sql`. Any prompt touching `Booking` or running a migration must VERIFY this constraint still exists (query `pg_constraint`).
- **Booking confirmation**: A booking flips to `confirmed` only on a verified PayMongo `payment.paid` webhook (HMAC-SHA256 signature) — never on client-side redirect. The one exception is credit-covered bookings (see Membership credit ledger below): no PayMongo involved, so confirmation happens via an atomic credit-balance decrement inside the booking's own DB transaction instead.
- **Money**: Stored as `Int` in centavos everywhere, matching PayMongo's native format. Never use floats for currency.
- **Booking state machine**: `pending_payment` → `confirmed` (webhook) or `cancelled` (hold expiry / failed payment).
- **Booking hold duration & expiry**: A `pending_payment` booking is held for `BOOKING_HOLD_MINUTES` (default 10) before being treated as abandoned — a plain env var, not admin-editable via the DB. Expiry has two layers: (1) expire-on-write — before any new booking insert, stale `pending_payment` rows for that resource/time are transactionally cancelled first, since the exclusion constraint only ignores `cancelled` rows; (2) a daily Vercel cron sweep for hygiene, cancels stale rows platform-wide (Hobby plan caps cron at once/day).
- **Pricing model**: Prices live in the DB (`PricingRule` for court/simulator rates, `AddOnPricingRule` for coaching/ball-boy rates), admin-editable without a code deploy. Each row is an explicit resource-type/member-tier/duration-tier combination — invalid combinations simply have no row. `src/lib/pricing-rule-combos.ts` is the single source of truth for valid combinations, enforced both server-side (`POST /api/admin/pricing-rules` and `.../add-on-pricing-rules` reject an invalid combo with 400) and client-side (`ResourcesTabs.tsx` shows no "+Add" for a cell the allow-list doesn't cover).
- **Customer & auth model**: `Customer.passwordHash` is nullable — null for non-member rows created from name/email/phone, set once a member activates via `/activate`. Member login uses Auth.js's `member-credentials` Credentials provider (email/password) checking this hash; `/account` gates on `session.user.role === 'member'`. Membership status for display purposes uses `Membership.endDate` as the source of truth for expiry (not the `status` column, which nothing auto-flips), falling back to the customer's most recent membership of any status, or an empty state if none exists. `Customer` is resolved by look-up-or-create on unique `email` (never blind-inserted), and `MembershipApplication.customerId` follows the same look-up-or-create-by-email rule (never nullable). `Booking.customerId` is nullable — a hold is created and its reference shown before name/email/phone are collected; `Booking.customer` attaches in a later `PATCH /api/bookings/[id]` step, and `GET /api/bookings/[id]`'s `customer` field is null-safe (`{ name } | null`) for the gap in between. `Booking.customerNameSnapshot`/`customerPhoneSnapshot` (nullable) capture the name/phone actually submitted for that specific booking at attach time, independent of any later change to the shared `Customer` row; every booking display site (admin Bookings list/detail, `GET /api/bookings/[id]`, `BookingConfirmation.tsx`, both booking-confirmation emails, PayMongo checkout billing) reads these snapshots instead of the live `Customer` join. `resolveCustomer()` (`src/lib/customer-resolution.ts`) only overwrites `Customer.name`/`.phone` on a mismatch when `passwordHash` is null — once a Customer has a real login account, a mismatched anonymous booking under that email can never overwrite it; non-member rows keep updating freely. Membership application/approval display logic deliberately still reads live `Customer.name`/`.phone`, not the booking snapshot.
- **`Booking.customerId` FK referential actions**: The FK to `Customer` is `ON DELETE RESTRICT ON UPDATE CASCADE` — deliberate. No Customer-delete feature exists; RESTRICT means a Customer with any booking history cannot be deleted, matching the app's disable-don't-delete precedent (`Resource.isActive`) over silently detaching history via `SET NULL`. A future Customer-delete feature must explicitly handle/reassign existing bookings rather than rely on cascade behavior.
- **Two-phase booking pricing**: A booking is priced twice. At hold creation (`POST /api/bookings`), pricing is provisional, always at the non-member rate (no customer/email exists yet). At customer attachment (`PATCH /api/bookings/[id]`), pricing is finalized — recomputed against the selections, but still always at non-member rate (`isMember: false`) regardless of the resolved `Customer`'s actual membership status, since this path is unauthenticated. The only thing that can change the total between hold and attach is a live `PricingRule`/`AddOnPricingRule` edit in that window; the wizard surfaces any change as a confirmation-required "final price is X (was Y)" notice before checkout. `src/lib/booking-pricing.ts` is the single source of truth for this math (parameterized by `isMember: boolean`); `src/lib/customer-resolution.ts` is the single source of truth for the look-up-or-create-then-check-membership logic feeding it, though the PATCH step ignores the returned `isMember`. Member rate and F&B credit are only available via the session-aware `POST /api/bookings` path (see Member-aware booking flow).
- **Member-aware booking flow**: `/book` serves both anonymous and member bookings, not a separate route. `src/app/book/page.tsx` reads the session server-side; if `session.user.role === 'member'`, it fetches that `Customer` and builds a `memberContext` (`name`/`email`/`phone`/`isActiveMember`) passed to `BookingPageClient.tsx`. `isActiveMember(customerId)` (`customer-resolution.ts`) is the single source of truth for active-membership checks on both the anonymous PATCH re-pricing path and the session-aware POST hold-creation path. When `POST /api/bookings` sees a member session, it resolves `isMember` itself and attaches `customerId` directly at hold creation — single-phase pricing, no PATCH round-trip. The anonymous PATCH path always prices at non-member rate regardless of whether the entered name/email/phone matches an existing member, since knowing a member's contact details must never be sufficient to obtain member pricing or spend their credit; the `Customer` record is still resolved/attached so the booking shows in that person's history once they log in. The ₱150/guest fee applies universally — every resource type and both rate tiers, independent of duration — shown on the Add-Ons step for every booking; `priceBooking()` applies it whenever `guestCount > 0`.
- **Admin/staff model**: Individual staff logins, not a shared account — multiple staff can hold the single current admin role, modeled via `AdminUser` (`role` is an enum with one value today, room for more later). `MembershipApplication.reviewedBy` and `BookingReschedule.performedBy` are real FKs to `AdminUser`, giving per-action accountability. Login is email/password (Auth.js v5, Credentials provider, JWT session, no adapter). Gating goes through a single shared `getActiveAdminSession()` helper (`src/lib/admin-session.ts`), used by `(protected)/layout.tsx` and every `/api/admin/*` route — it re-verifies `AdminUser.isActive` fresh from the DB on every request, so a deactivated admin's already-open session is rejected on its next request, not just their next login. `middleware.ts` does not appear to execute in this Next 16.3.0/Turbopack-on-Windows dev setup, so gating relies entirely on these per-route/layout checks, not the matcher.

- **Admin panel is tablet-and-up only**: No mobile-width (375px-class) support is planned for the admin panel — it's a staff tool used on tablets/desktops in practice, not a public-facing surface. Future VERIFY steps for admin-panel work should not budget a mobile-width check by default; the public site and `/account` remain fully mobile-responsive, unchanged by this decision.
- **`BookingReschedule` immutability**: This model has no `updatedAt` and its rows are never edited after creation — each row is a permanent audit entry (original slot, new slot, reason, admin, timestamp). If a logged reschedule entry is ever wrong, the fix is to insert a new correcting row, never to edit the original.
- **`Payment` ↔ `Booking` relationship**: `Payment.bookingId` is a direct, nullable FK to `Booking` (not polymorphic) — nullable because a future POS transaction will also create a `Payment` with no `Booking` attached; chosen over a polymorphic `referenceType`/`referenceId` pattern for real DB-enforced referential integrity. `Payment` also carries nullable `paymongoPaymentId` (PayMongo's pay_xxx id, distinct from `paymongoPaymentIntentId`/`paymongoCheckoutSessionId`) for staff cross-reference, and nullable `paymongoFeeCentavos`/`paymongoNetAmountCentavos` (fee+foreign_fee combined / actual settlement amount) — all three captured from the `payment.paid` webhook, booking-`Payment`-only (`MembershipPayment` untouched), null for credit-covered bookings and any pre-existing row (not backfilled).
- **Membership credit ledger**: `Membership.creditBalanceCentavos` is a cached running total, not the source of truth — `MembershipCreditTransaction` (immutable, `createdAt`-only) logs every event that changes it (activation, future POS spend, manual adjustments). `CreditTransactionReason` has three values: `activation`, `renewal`, `booking_redemption`. `amountCentavos` is positive for credits, negative for debits, so `SUM(amountCentavos)` per membership always recovers the balance. POS will only add a further `reason` value, not a new table.
- **Membership payment model**: Tier-activation payment for an approved application is tracked by its own `MembershipPayment` model (`applicationId`, `tier`, `amountCentavos`, `status`, PayMongo checkout-session/payment-intent ids, `paidAt`) rather than a `Payment.membershipApplicationId` FK — `Payment` stays booking-scoped. `POST /api/membership-payments` creates or resumes a PayMongo Checkout Session for an approved application (reuses a `pending` row rather than duplicating). Approving an application only flips `status` to `approved` and emails a payment link — the `Membership` row (plus credit-ledger entry and activation token) is created only once payment confirms via the PayMongo webhook's `metadata.membershipPaymentId` branch (alongside the pre-existing `metadata.bookingId` branch, dispatched by which metadata key is present). `MembershipPayment.applicationId`/`Membership.applicationId` are both nullable and `MembershipPayment` carries a direct `customerId`, supporting self-service renewal (a new `Membership` with `applicationId: null`, keyed by that null on `MembershipPayment`). `MembershipPayment.initiatedByAdminId` (nullable FK to `AdminUser`) tracks admin-initiated renewal-link sends, set only by the admin "Send Renewal Link" action.
- **Guest fee rate storage**: The flat ₱150-per-additional-guest surcharge (every resource type, both rate tiers, independent of duration) lives in its own `GuestFeeRule` table (`id`, `amountCentavos`, timestamps) rather than as a `PricingRule` column or hardcoded constant, keeping it admin-editable without conflating it with `PricingRule`'s duration-tiered rows. Only one row exists; the table shape allows future variation (e.g. per-sport guest fees) without restructuring. Edit-only, permanently — no create/delete, by design.
- **Member check-in (QR + fallback code)**: Front-desk check-in resolves from a stable per-`Customer` identifier pair, always created/rotated together: `checkInToken` (`crypto.randomBytes(24).toString('base64url')`, rendered as a `data:image` QR via the `qrcode` package) and `checkInCode` (zero-padded 6-digit fallback, unique, collision-retry generated). `src/lib/check-in-token.ts` generates/regenerates both (`POST /api/account/check-in-token/regenerate`). Admin resolution (`/admin/check-in`, Scan tab via `html5-qrcode` + Enter Code tab) delegates both `GET /api/admin/check-in/[token]` and `GET /api/admin/check-in/code/[code]` to one shared `resolveAdminCheckInResult` (`src/lib/admin-check-in.ts`), rendered through the same `CheckInResultCard`. Code-entry attempts are rate-limited per admin: `CheckInLookupAttempt` (FK'd to `AdminUser`, cascade delete) logs failed lookups, and `src/lib/check-in-rate-limit.ts` blocks the 11th failure within any rolling 5-minute window per admin (expire-on-write, no cron). The QR/token path is excluded from rate-limiting — its 24-random-byte space isn't brute-forceable.
- **Row Level Security (RLS)**: All application tables have RLS enabled with explicit deny-all policies for the `anon` and `authenticated` Supabase roles. The app's real DB access goes through Prisma via `DATABASE_URL`/`DIRECT_URL` (Supabase's privileged `postgres` role, which bypasses RLS), so this only closes off the Supabase anon-key REST API path. Master SQL lives at `prisma/manual-sql/enable-rls-deny-all.sql`. Every new table must enable RLS with deny-all policies in the same migration that creates it (see Coding Conventions); any migration-touching prompt should VERIFY policies still exist (query `pg_policies` and `pg_class.relrowsecurity`).
- **Bulletin-triggered resource auto-disable**: A bulletin can optionally claim one or more `Resource` rows via a `BulletinResource` join table (`bulletinId`, `resourceId`, unique pair, both FKs cascade-delete) and, while its claim is active, force them offline by setting `Resource.isActive: false` (reusing the existing flag, not a second one). `Bulletin.autoDisableResources` (boolean, default `false`) is the admin's per-bulletin opt-in; a bulletin is "actively claiming" its resources whenever `isPublished && autoDisableResources && (expiresAt IS NULL OR expiresAt > now()) && (eventStartAt IS NULL OR eventStartAt <= now())` — this predicate, `bulletinShouldDisableResources()` in `src/lib/bulletin-resource-disable.ts`, is evaluated fresh everywhere, never cached. The `eventStartAt` clause lets a closure be announced in advance without disabling immediately. **Manual always wins**: `Resource.disabledReason` (`ResourceDisabledReason` enum: `manual | bulletin`, null when active) tracks which mechanism most recently disabled a resource — a manual admin Disable/Enable (`PATCH /api/admin/resources/[id]`) always stamps/clears `'manual'` regardless of any bulletin claim, and `releaseBulletinResourceDisable()` only re-enables a resource currently tagged `'bulletin'`, never stealing back a manual disable; `applyBulletinResourceDisable()` only disables a resource that's currently active. Releasing checks every other published, auto-disabling, unexpired bulletin still linking to that resource before re-enabling. The pre-existing free-text admin note is `Resource.disabledNote` (renamed from the original `disabledReason` to free that name for the enum). The three bulletin API routes (`POST`/`PATCH`/`DELETE /api/admin/bulletin[/[id]]`) each wrap their handler in one `prisma.$transaction`; a bulletin's delete releases every linked resource first. The daily `/api/cron/expire-bookings` cron (same schedule, no second cron entry) has two extra steps beyond booking-hold expiry: release resources for any published, auto-disabling bulletin whose `expiresAt` has passed, and apply disables for any whose `eventStartAt` has passed — both only run once daily (Vercel Hobby cron cap), so effect can lag by up to a day. `affectedFacility` and `bulletinNotExpiredWhere()`'s public-surface filtering are untouched, a separate mechanism alongside this one. `ResourcesTabs.tsx` shows a "Disabled by bulletin" note next to the Inactive badge when `disabledReason === 'bulletin'`; the admin Bulletin list shows a bulletin's linked resource names inline when `autoDisableResources` is on.
- **Transactional email sending domain**: `winstonsipandserve.club` is verified in Resend (SPF/DKIM live, DMARC monitor-only `p=none`). Transactional emails send from `no-reply@winstonsipandserve.club` with `reply-to` set to `winstonsipandserve@gmail.com` — see `src/lib/resend.ts`.
- **Password reset**: `PasswordResetToken` (mirrors `MemberActivationToken`'s shape — `customerId` FK, `tokenHash`, `expiresAt`, `usedAt`) backs member self-service password reset; expiry is `PASSWORD_RESET_TOKEN_HOURS` (default `1`), deliberately shorter than activation's 48 hours since a reset link guards an existing account. `POST /api/auth/forgot-password` is enumeration-safe: always returns the identical `200 { message: "If that email is registered, we've sent a password reset link." }` regardless of outcome, only actually creating a token/email if the `Customer` is found and already activated. `POST /api/auth/reset-password` mirrors `/api/activate`'s validation/transaction shape (set `passwordHash`, stamp `usedAt`, one `$transaction`), with a deliberately vaguer 404 ("Invalid or expired reset link") than activation's.
- **Transactional email branding**: All transactional emails share one branded layout via `buildBrandedEmail(...)` in `src/lib/email-templates.ts` (generic/parameterized) rather than each call site building its own HTML — current consumers: `sendActivationEmail`, `sendMembershipPaymentEmail`, `sendPasswordResetEmail`, `sendRejectionEmail`, `sendBookingConfirmationEmail`, `sendMembershipExpiryReminderEmail`, `sendMembershipExpiredEmail`, `sendMembershipRenewalEmail`, `sendRenewalPaymentLinkEmail`. The layout's logo is served from a public Supabase Storage bucket, `email-assets` (mirrors `bulletin-images`' shape: public, one deny-by-default-except-SELECT RLS policy for `anon`/`authenticated`, writes service-role-only — master SQL at `prisma/manual-sql/email-assets-bucket.sql`). Asset upload into this bucket is manual via the Supabase dashboard, not app-driven. The shared `ledgerRow` helper supports an `indent` option, alongside a `ledgerSectionHeader` helper, used by the booking-confirmation and staff-booking-notification emails to show an itemized Add-ons breakdown (Guests/Ball Boy/Coaching) under a base-rate Price row.
- **Membership certificate PDF**: `@react-pdf/renderer` (v4.9.0, an approved dependency exception scoped specifically to this file) generates `src/lib/membership-certificate-pdf.tsx`, attached only to the first-time activation `sendActivationEmail` (never renewal, never the plain activation-link case). It registers Noto Sans as a real font (fetched from Google Fonts' CDN at render time) instead of react-pdf's built-in Helvetica, since Helvetica's base-14 encoding has no glyph for the ₱ sign `formatCentavos` produces. "Approved by Admin" on the PDF is an intentional static label, not tied to the actual reviewing `AdminUser`/`reviewedBy` relation.
- **Local-dev database connection**: `.env.local`'s `DATABASE_URL` intentionally points at Supabase's session-mode pooler (port `5432`, no `pgbouncer=true`) rather than the transaction-mode pooler (port `6543`) used for deployed environments — transaction-mode pooling forces `DEALLOCATE ALL` before reusing prepared statements, measurable overhead in local dev where a single long-lived connection is safe. Deployed environments (Vercel staging/production) must keep the pooled `:6543` connection so serverless functions don't exhaust Supabase's connection limit. The measured connection-priming floor for a fresh pooled connection is ~300ms per `/admin/*` navigation (Vercel Function Region and Supabase are both `syd1`, matching). Reducing this floor project-wide (Prisma Accelerate, a different pooling strategy, or Vercel Fluid Compute) is an open investigation.
- **Business hours**: Bookings are restricted to **6:00 AM–10:00 PM Asia/Manila**, uniformly across all resource types. This is a hardcoded constant in `src/lib/business-hours.ts` (`BUSINESS_OPEN_HOUR`/`BUSINESS_CLOSE_HOUR`), not admin-editable yet. Enforced server-side in `POST /api/bookings` (400 on any out-of-hours request, even bypassing the UI) and reflected client-side by `GET /api/availability` and the booking wizard's time-slot grid.
- **`GET /api/availability`**: Public, no-auth endpoint (same trust level as `GET /api/resources`) that returns which time ranges are already occupied for a given `resourceId` + PH calendar `date`, so the booking wizard's time-slot grid can gray out unavailable slots before submit. Returns `{ busy: [{ start, end }] }` only — no pricing, no customer data. Uses the same "counts as occupying the slot" definition as booking creation (see `src/lib/booking-hold.ts` below), evaluated at request time, so a stale `pending_payment` hold correctly shows as available.
- **`src/lib/booking-hold.ts` extraction**: `HOLD_MINUTES` and the "is this booking currently holding/occupying its slot" condition (`confirmed`, or a `pending_payment` row younger than the hold window) are extracted here so `GET /api/availability` and `POST /api/bookings` both import the same definition — this guarantees the hold window can never drift between "what counts as available" and "what actually gets held."
- **PayMongo integration shape**: PayMongo Checkout Sessions (hosted, redirect-based) is the chosen integration — not raw Payment Intents + client-side Elements. `Payment` carries `paymongoCheckoutSessionId` (set at checkout-session creation) and `paymongoPaymentIntentId` (resolved once payment completes, from the webhook payload). Bookings confirm only via a verified `payment.paid` webhook (HMAC-SHA256, `Paymongo-Signature` header). Whenever a stale `pending_payment` hold is cancelled (expire-on-write or the daily cron), its linked PayMongo checkout session is also actively expired via PayMongo's Expire Checkout Session endpoint (best-effort), closing the gap where a customer could pay into an already-released slot.

  **Real webhook payload shape** (self-signed test payloads got this wrong — real PayMongo deliveries differ): event type is `data.attributes.type`, matched against `'payment.paid'` (not `'checkout_session.payment.paid'`). Payment fields all live under `data.attributes.data.attributes` (not `data.attributes.data` directly): `metadata.bookingId`, `status` (must equal `'paid'`), `payment_intent_id` (a flat string field, not a nested object), and `paid_at` (Unix seconds — converted via `new Date(paid_at * 1000)`).
- **Public-site color palette**: Defined as Tailwind v4 `@theme` tokens in `src/app/globals.css` — `--color-brand-dark: #321E1E` (dominant), `--color-brand-mid: #4E3636` (secondary), `--color-accent-primary: #CD1818` (primary CTA color, used sparingly), and `--color-accent-teal: #116D6E` (tertiary accent, applied at `/cafe-bar`'s Café/Bar mode toggle and `/membership`'s tier-card checkmarks only). `--color-brand-light`/`--color-accent-light` (cream) are unchanged. Every component reads these values via the shared tokens, never hardcoded hex. This is unrelated to the separate "don't use Tailwind's default green-100/800 for status badges" convention. The admin panel intentionally stays neutral-gray and does not use these tokens.
- **Corner-radius system**: The public-site corner radius follows a small, deliberate scale defined as Tailwind v4 `@theme` tokens in `src/app/globals.css` — `--radius-input: 0.5rem` (8px), `--radius-card-inline: 0.75rem` (12px), and `--radius-card: 1rem` (16px) — plus Tailwind's own `rounded-none`/`rounded-full` utilities used directly. Buttons/CTAs and the booking wizard's selector-chip controls (`SportStep`/`CourtStep`/`TimeSlotGrid`/`Calendar`'s nav+day buttons/`AddOnsStep`'s toggles+stepper+pax buttons/`MembershipApplicationForm`'s tier rows/`DateTimeStep`'s duration pills) are sharp `rounded-none`; text/email/password inputs are `rounded-input`; nested inline notices and inset thumbnails are `rounded-card-inline`; primary content cards, modal dialogs (`Modal.tsx`'s `brand` variant only — admin `neutral` stays `rounded-2xl`), and image tiles are `rounded-card`; badges/pills/step-indicator dots stay `rounded-full`. ## Scope & Future Extension

**Current build**: Booking system (tennis / pickleball / golf-sim) + Admin panel to manage it. This is the entire scope right now.

**Planned, not yet happening**: The client wants to extend this same platform with a POS system later. POS is **not** being built now — but the schema should be designed so that extension doesn't force a rewrite. Concretely:

- **Customer/User model**: Keep it generic enough that a future POS transaction and a booking can both reference the same customer record. Don't build booking-only customer fields that a shared customer model would later have to duplicate or migrate away from.
- **Payment/Transaction model**: PayMongo is shared ground between booking and POS. Keep payment records general (amount, method, status, reference) rather than booking-specific fields baked directly into a `BookingPayment`-style table, since POS sales will also need PayMongo transactions.
- **Admin panel / roles**: Since the admin panel is in scope now, design its permission/role model assuming more resource types will exist later (POS orders, inventory), even though only booking-related roles exist today.

**What NOT to do**: Don't create `Product`, `Inventory`, `POSOrder`, or any POS-specific tables now. That's premature scope creep. The goal is only to avoid painting the booking schema into a corner — not to pre-build POS.

## Coding Conventions

- **Prisma schema**: PascalCase model names, snake_case DB columns via `@map`, `cuid()` IDs, money fields as `Int` (centavos), required `createdAt`/`updatedAt` timestamps on all models — **except `BookingReschedule`**, which is `createdAt`-only by design (see "Architecture Decisions" for why).
- **New tables**: every new table must enable RLS with explicit deny-all policies for `anon` and `authenticated` in the same migration that creates it — see Architecture Decisions → Row Level Security. Don't defer this to a follow-up migration.
- **Test/cleanup script safety**: Any disposable script under `scripts/` that deletes data as part of a testing pass must scope every delete to explicitly recorded test-created row IDs (captured at creation time, passed directly to the delete call) — never to a resource-ID, date-range, or time-window query, even one that looks safe. A range-based delete can silently match pre-existing real data alongside the intended test rows. This rule exists because of a real incident — see PROGRESS.md's 2026-09-04 admin business-logic testing pass entry for the concrete case.
- **API routes**: Route handlers live under `src/app/api/`, return `Response.json(...)` with explicit status codes (400 validation, 401 auth, 409 conflict, 500 unexpected). Member status for pricing is always derived server-side (`Customer` → active `Membership` check), never trusted from the request body or a client session — this holds even once real Auth.js wiring for member login is built. A shared Prisma client singleton lives at `src/lib/prisma.ts`; future routes should import it rather than instantiating `new PrismaClient()` per-route.
- **Components**: Folder-per-feature under `src/components/` (e.g. `src/components/booking/`), PascalCase filenames matching the exported component (`BookingForm.tsx`, `BookingConfirmation.tsx`). Add `'use client'` at the top of any component that uses state, effects, or browser APIs; leave server components (e.g. page files that don't need interactivity) without it. Shared, non-component helpers (formatting, etc.) live under `src/lib/`.
- **Multi-step wizards**: Individual steps live in a `steps/` subfolder under the owning feature (e.g. `src/components/booking/steps/`), one component per step plus a `StepIndicator`. All wizard state (including the current step) is lifted to the top-level orchestrator component and passed down as props — steps themselves hold no state — so navigating Back and forward again never resets a previously entered value.
- **Error handling**: API routes return `Response.json({ error: '<message>' }, { status })` on failure — a single `error` string field, no nested error objects — using the status codes above (400/401/409/500). Client components that call these routes branch on `res.status` (not just `res.ok`) to distinguish expected outcomes (e.g. 409 conflict) from generic failures, surface `400` bodies by reading `json.error` directly into the UI, and fall back to a generic inline message for network errors or unexpected statuses — never a route change or thrown/uncaught exception, so the user's in-progress form state is preserved.
- **Auth.js config split (Edge Runtime)**: `middleware.ts` runs on Next.js's Edge Runtime, which can't load Node-only APIs — Prisma, or `crypto` (used by `src/lib/admin-auth.ts`'s password hashing/verification). Any config that touches those must live only in the full root `auth.ts` (which spreads `auth.config.ts` and adds the two Credentials providers); the root `auth.config.ts` itself must stay edge-safe — `providers: []`, plus `session`/`pages`/`callbacks` (the `jwt`/`session` callbacks live here too, since they're pure object manipulation on the token/session with no Prisma/`crypto` involved). `middleware.ts` imports only `auth.config.ts` and builds its own lightweight `NextAuth(authConfig).auth` wrapper from it — it must never import `auth.ts` directly, since that would pull Prisma/`crypto` into the Edge bundle.
- **Dependency exceptions**: New dependencies are avoided by default. `next-auth@5` (beta) was installed 2026-08-19 as an explicit approved exception, scoped specifically to admin auth (Credentials provider + JWT sessions) — not a general policy change. `recharts` was installed 2026-08-28 as an explicit approved exception, scoped specifically to the admin Dashboard tab's charts (bookings trend, revenue trend, resource breakdown) — not a general charting-library policy change. `qrcode` (plus `@types/qrcode`, since the package ships no bundled types) was installed 2026-08-31 as an explicit approved exception, scoped specifically to rendering the member-portal check-in QR code (`src/lib/check-in-token.ts`) — not a general policy change. `html5-qrcode` (ships its own bundled types, no separate `@types/` package needed) was installed 2026-08-31 as an explicit approved exception, scoped specifically to the admin Check-In tab's camera-based QR scanner (`src/components/admin/CheckInScanner.tsx`) — not a general policy change. `@react-pdf/renderer` (v4.9.0, ships its own bundled types) was installed 2026-09-01 as an explicit approved exception, scoped specifically to the membership-certificate PDF attached to first-time activation emails (`src/lib/membership-certificate-pdf.tsx`) — not a general PDF/reporting-library policy change. Future dependency additions still need the same kind of explicit approval before installing.

2. Finalized prompts are pasted into Claude Code, run against this local repo.
