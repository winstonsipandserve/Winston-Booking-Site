# CLAUDE.md

Instructions for Claude Code working in this repository.

**Winston Sip and Serve** — a booking platform and admin panel for a single-venue sports facility (tennis, pickleball, golf simulator bays) with an attached café and bar. Next.js 16 App Router + TypeScript, Prisma, Supabase, Auth.js v5, PayMongo, Resend, deployed on Vercel.

This file covers *how to work here*. Project knowledge lives in `docs/`.

---

## Documentation Architecture

```
docs/          Shared project knowledge — tool-agnostic, the source of truth
CLAUDE.md      Claude Code instructions (this file)
.claude/       Claude Code configuration and skills
AGENTS.md      Auto-generated by `next dev` — do not hand-edit
```

`docs/` must stay **tool-agnostic** so any coding agent can use it. Never put Claude-specific instructions there, and never duplicate `docs/` content back into this file.

### Which document to read

**Read the relevant document before planning work in that area.** Do not answer from memory or infer domain rules from code alone — several rules exist for reasons the code does not show.

| Question | Read |
|---|---|
| Business rules, pricing, membership, domain concepts | [docs/business.md](docs/business.md) |
| What the application currently does | [docs/features.md](docs/features.md) |
| How a process runs end to end | [docs/workflows.md](docs/workflows.md) |
| Stack, code layout, external services, environment | [docs/architecture.md](docs/architecture.md) |
| Models, enums, relationships, constraints | [docs/database.md](docs/database.md) |
| Why something was built this way | [docs/decisions.md](docs/decisions.md) |
| Known bugs, deferred work, planned features | [docs/roadmap.md](docs/roadmap.md) |

**[docs/decisions.md](docs/decisions.md) is the important one.** It records choices that must not be silently undone. If a task seems to require deviating from a decision recorded there, raise it before implementing rather than working around it.

### Keeping documentation current

When work changes something a document asserts, update that document in the same change. Put each fact in exactly one place and cross-reference rather than copying.

**There is no progress log, and one must not be created.** The project deliberately does not track state chronologically — `git log` carries history. `docs/` describes the *current* state and is edited in place.

## Working Agreement

### Planning and approval

- Tasks are discussed and planned **directly in conversation here**, against the live repo. There is no external prompt-drafting step. If you find docs or conventions written around "the originating prompt," they are stale.
- **Ask before implementing** when: the task would deviate from something in `docs/decisions.md`; it needs a new dependency; it changes the database schema; it touches payment, auth, or booking-conflict logic; or the requirements are ambiguous enough that two readings would produce materially different work.
- Otherwise make routine judgment calls and proceed.

### Git — manual, always

**Never run `git add`, `git commit`, or `git push` in this repository.** Work that produces a commit ends with an explicit git block for Arjay to review and run. This applies to every git operation, including branch merges.

### Branch promotion

Promotion is manual, with no automated merge gates.

- **`dev` → `staging`** — once the change has passed local verification.
- **`staging` → `main`** — only after verifying against the deployed `staging` environment itself, not just locally. `main` auto-deploys to production.
- Before any payment-touching promotion to `main`, confirm the PayMongo key swap. See [docs/roadmap.md](docs/roadmap.md).

### Verification

- Output is manually reviewed and validated, including browser verification where relevant. Nothing is auto-approved.
- **Nothing in this project is currently treated as verified** — see [docs/roadmap.md](docs/roadmap.md). Do not cite a prior QA pass as evidence.
- There are no automated tests. Verification means running the affected flow and checking real data or real output.
- Report outcomes honestly: if something failed, say so with the output; if a step was skipped, say that.

## Coding Conventions

### Prisma and the schema

- PascalCase model names, snake_case columns via `@map`, `cuid()` ids.
- **Money is always `Int` in centavos.** Never a float.
- `createdAt`/`updatedAt` on every model, except immutable audit models, which are `createdAt`-only by design.
- **Every new table must enable RLS with explicit deny-all policies** for `anon` and `authenticated` in the same migration that creates it. Never defer this.
- **Never edit an applied migration** — it changes the checksum and breaks the next deploy.
- Any change touching bookings or running a migration must verify the overlap exclusion constraint and RLS policies still exist.

### API routes

- Handlers live under `src/app/api/`, returning `Response.json(...)` with explicit status codes: 400 validation, 401 auth, 409 conflict, 500 unexpected.
- Errors are a **single `error` string field**, never a nested error object.
- **Member status is always derived server-side** from the customer's active membership — never trusted from a request body or a client session claim.
- Import the shared Prisma singleton from `src/lib/prisma.ts`; never instantiate a new client per route.

### Components

- Folder-per-feature under `src/components/`, PascalCase filenames matching the exported component.
- Add `'use client'` only to components that use state, effects, or browser APIs. Leave server components without it.
- Shared non-component helpers go in `src/lib/`.
- **Multi-step wizards**: steps live in a `steps/` subfolder, one component per step plus a step indicator. **All state, including the current step, is lifted to the top-level orchestrator** and passed down — steps hold no state of their own, so navigating back and forward never resets a value.

### Client-side error handling

Components calling an API branch on `res.status`, not just `res.ok`, so an expected outcome (like a 409 conflict) is distinguishable from a generic failure. Surface a 400 body's `error` directly into the UI and fall back to a generic inline message for network or unexpected errors — **never a route change or an uncaught exception**, so the user's in-progress form state survives.

### Auth.js and the Edge Runtime

`middleware.ts` runs on the Edge Runtime and cannot load Prisma or Node's `crypto`.

- Anything touching those lives **only** in the root `auth.ts`.
- `auth.config.ts` must stay edge-safe — empty providers, plus session/pages/callbacks.
- **`middleware.ts` must never import `auth.ts`.**

Note that `middleware.ts` does not execute in this local dev setup, so every gated route carries its own auth check. Any new route under the matcher must include one — never rely on the matcher alone.

### Throwaway-script data safety

Any disposable script that deletes data must scope **every** delete to explicitly recorded row IDs, captured at creation time and passed directly to the delete call.

**Never a resource-ID, date-range, or time-window query, even one that looks safe.** A range-based delete can silently match pre-existing data alongside the intended test rows. This rule exists because exactly that happened.

### Dependencies

New dependencies are avoided by default and need explicit approval before installing. Five narrowly scoped exceptions have been granted — see [docs/decisions.md](docs/decisions.md). Reuse what is already there before reaching for something new.

### Design work

Do not re-derive a palette, radius scale, or dark-mode token set per task — they are fixed. See the design system section of [docs/decisions.md](docs/decisions.md).

## Skills (`.claude/skills/`)

Use these when the task matches; don't reinvent what they already encode.

**Project-specific:**

- **`paymongo-integration`** — payment and webhook work.
- **`booking-conflict-prevention`** — booking creation, availability, or scheduling logic. Any task using it must verify the exclusion constraint is actually present in the database, not assume it survived a migration.
- **`prisma-schema-conventions`** — any edit to `schema.prisma`.

> Both `paymongo-integration` and `prisma-schema-conventions` currently contain details that have drifted from the implementation. Trust [docs/architecture.md](docs/architecture.md) and [docs/database.md](docs/database.md) over a skill where they disagree.

**General design and motion** (installed via `npx skills`, not project-specific): `impeccable` (broad frontend audit and polish), `emil-design-eng` (UI craft), `animate` (build an animation), `review-animations` (critique motion), `improve-animations` (codebase-wide motion audit), `prototype` (build variants to choose between). Reach for these on visual polish passes. `impeccable`'s hook and image-generation features are off by default — read its own SKILL.md before enabling them.

Five skills (`apple-design`, `ask-sonner`, `pick-ui-library`, `animation-vocabulary`, `find-animation-opportunities`) were removed as a poor fit for this project. Don't reinstall without a concrete reason.

**Deliberately not skills:** the git workflow and browser verification are manual gates — an ambient skill would conflict with them.

- **Context7** — current Next.js / Prisma / PayMongo / Auth.js documentation lookups.
