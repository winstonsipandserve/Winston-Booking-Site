## Build Status

- **Stack**: Next.js 16 (App Router) + TypeScript, Prisma 6.19.3, Supabase (Postgres/RLS/Storage), Auth.js v5, PayMongo (Checkout Sessions API), Resend, Tailwind v4 (CSS-first `@theme`, no config file). Deployed to Vercel.
- **Schema**: 23 Prisma models. `booking_no_overlap` exclusion constraint and RLS deny-all (all tables, `anon`+`authenticated`) both live as isolated migrations, master SQL under `prisma/manual-sql/`. Resource inventory: 1 tennis court, 3 pickleball courts, 1 tennis sim, 2 pickleball sims, 2 golf sims.
- **Booking + payment flow**: Complete end-to-end, member-aware. Anonymous: announcement gate → 5-step wizard → hold created on Confirm (`customerId: null`, provisional non-member pricing) → Payment page (reference shown immediately; Pay Now attaches customer, re-prices at non-member rate) → PayMongo Checkout (auto-redirect) → `/book/confirmation`. Logged-in member with an active `Membership`: `/book` detects the session server-side, hold creation prices at the member rate and attaches `customerId` directly (no PATCH round-trip); Payment skips straight to a "Booking under {name} ({email})" summary. The session-aware member path supports full-or-nothing F&B-credit redemption — if the credit balance fully covers the total, `POST /api/bookings` confirms instantly with no PayMongo checkout and debits atomically; otherwise an advisory modal explains the member will be charged in full via PayMongo with credit untouched. The guest-count control (universal ₱150/guest fee) shows on Add-Ons for every booking; `/book/confirmation` renders a booking-details card (Booking Reference, Resource, Date & time, Duration, Guests, Ball Boy, Coaching — no prices) and a pricing card (base Price, itemized Add-ons total, Total).
- **Marketing site**: All 6 pages done — Home, Book Now, News, Café & Bar, Membership (info + `/membership/apply`), About. Navbar is `fixed`, transparent-over-Hero → solid-on-scroll on `/`, `/about`, `/membership`, `/cafe-bar`; `/book` and `/news` have no hero and force the navbar permanently solid via `FORCE_SOLID_PAGES` in `Navbar.tsx`. `/news` has a 7-pill category filter (All + 6 categories, URL-driven via `?category=`) backed by `CATEGORY_LABELS`. The public-site corner-radius system (`--radius-input`/`--radius-card-inline`/`--radius-card` tokens) is applied sitewide with no exceptions remaining. Placeholder content pending client input: Home Hero copy, About's Our Story, Footer contact info, News social links.
- **Auth**: Email/password, live for admin (`credentials` provider) and member (`member-credentials` provider), JWT sessions, no adapter. Every `/api/admin/*` route + `(protected)/layout.tsx` gate through the shared `getActiveAdminSession()` helper. `/account` gates on `role === 'member'`, shows real `Customer`/`Membership`/`Booking` data. Member sign-in on `/login` is client-side `signIn()` (Navbar updates immediately) with a password show/hide toggle; the public Navbar's Sign Out requires confirming a modal first.
- **Forgot password**: Live end-to-end — `PasswordResetToken` (1hr expiry), enumeration-safe `/api/auth/forgot-password` (always 200), `/api/auth/reset-password`, `/forgot-password` + `/reset-password` pages.
- **Membership application/approval**: Submission (`/membership/apply`) → admin review (`/admin/memberships`) → approve/reject mutation, live. Approval only flips status + sends a "complete your payment" email with a `/membership/pay/[id]` link — `Membership` + credit ledger + `MemberActivationToken` are created by the PayMongo webhook on confirmed tier-activation payment. Rejection sends a branded email with the admin's reason. Staff receive a `[Membership Application]` notification email on every submission. `POST /api/membership-applications`'s duplicate-check is derived-display-status-aware (pending/awaiting-payment/active/expired all 409 with distinct messages; only a rejected most-recent application allows reapplication), surfaced via a dismissible `Modal` on 409.
- **Membership tier-activation payment**: Live end-to-end — `POST /api/membership-payments` (create-or-resume PayMongo checkout, `MembershipPayment` model) and public `GET /api/membership-applications/[id]` back `/membership/pay/[id]` and `/membership/pay/confirmation`. Self-service renewal for expired members is live — session-gated `POST /api/account/membership-renewal`, public `GET /api/membership-payments/[id]`, `/account/renew` + confirmation, `MembershipStatusCard`'s "Renew Membership" CTA. Admin-side manual fallback is also live — `POST /api/admin/memberships/[id]/send-renewal-link` + public `POST /api/membership-payments/[id]/checkout` back `/membership/renew/[id]`, surfaced via a "Send Renewal Link" button (only when expired). `handleMembershipPaymentWebhook` sends staff notifications on both activation and renewal paths.
- **Membership credit top-up**: `Payment` now also represents a credit top-up (nullable, non-unique `membershipId`, alongside the pre-existing nullable-unique `bookingId`) via 3 methods — `paymongo` (self-service), `cash`, `manual_online` (both admin-logged, front-desk). Self-service: session-gated `POST /api/account/membership-topup` (4 fixed presets — ₱1,000/2,500/5,000/10,000 — against the member's active `Membership`) creates a PayMongo Checkout Session; the webhook's new third dispatch branch (`topUpPaymentId` metadata key, distinct from `bookingId`/`membershipPaymentId`) flips the Payment to paid, logs a `MembershipCreditTransaction` (`reason: top_up`), increments `Membership.creditBalanceCentavos`, and sends a new `sendCreditTopUpConfirmationEmail`. `MembershipStatusCard`'s new "Top Up F&B Credit" 4-button row shows only for an active (non-expired) membership — the mirror-image gate of the existing Renew CTA; `/account/topup/confirmation` polls status the same way `/account/renew/confirmation` does. Admin-side: `POST /api/admin/memberships/[id]/credit-topup` (note: this route's `[id]` is a Membership id directly, unlike sibling routes under the same folder which take a MembershipApplication id) records an already-`paid` Payment + ledger entry + `AdminActivityLog` (`membership_credit_topup_added`) in one transaction, gated to a currently-active membership; surfaced via a new "Add Credit" button (Cash/Online mode toggle, note required for cash / reference required for online) next to the admin detail page's Credits stat, shown only when `displayStatus === 'active'`.
- **Transactional email**: `buildBrandedEmail` (shared layout) has 13 consumers covering activation, rejection, forgot-password, booking confirmation, staff notifications (booking/membership-application/membership-activation/membership-renewal), membership-payment-link, membership-expiry-reminder/expired/renewal, and renewal-payment-link — all live, sending from verified domain `no-reply@winstonsipandserve.club`, reply-to `winstonsipandserve@gmail.com`. First-time membership activation emails carry a branded PDF membership certificate (`@react-pdf/renderer`); the booking-confirmation and staff-booking-notification emails show a base-rate Price row plus an indented Add-ons breakdown (Guests/Ball Boy/Coaching).
- **Admin panel**: Dashboard (6 stat cards — Bookings Today, Booking Revenue This Month, Membership Revenue This Month, Pending Applications, Active Memberships, Resource Utilization — plus 2 recharts charts: the Revenue Trend chart has a Booking/Membership view toggle alongside its Range (3mo/6mo/12mo/YTD) selector, each view with its own Breakdown options (Booking: Total/By Resource Type; Membership: Total/By Tier/Top-Ups), and a resource-type pie chart; Recent Bookings/Pending Applications lists round it out, all wired to real Prisma queries via `getDashboardData()`). Booking Revenue counts only `Payment` rows with `bookingId` set; Membership Revenue counts `MembershipPayment` (activation/renewal) plus `Payment` rows with `membershipId` set (top-ups) — the two never overlap. Bookings (list with a functional search bar and neutral Filter modal, both server-side and composable; both list and detail show the actual grand total via `bookingGrandTotalCentavos()`, PayMongo Payment ID, and Net Amount; detail page's Payment card also shows PayMongo Fee; Reschedule is a collapsed-by-default foldable section; list's Export button is functional). Memberships (list/detail + approve/reject; status filter splits on derived display status via a Filter modal; functional Export; a pending application's detail page shows a lightbox `IdentityVerificationGallery.tsx` and a sticky Approve/Reject bottom bar; an active/expired member's detail page shows a header with member name + "Member since", a 4-cell Quick Stats row, Member Information/Membership Details cards, a collapsible Verification Documents section, and Credit Transaction History/Booking History lists with 10-row caps). Resources & Pricing (tabbed Courts/Simulators/Guest Fee; resources are edit+disable/enable only; Pricing/Add-on rows have full create/edit/delete gated by the `pricing-rule-combos.ts` allow-list; Guest Fee stays edit-only). Bulletin (full CRUD + optional image upload; 7-category enum including `Promotion`, each with its own required-field rules; can optionally link `Resource` rows to auto-disable them while published — see CLAUDE.md's Architecture Decisions). Check-In (camera QR scan + rate-limited manual code fallback). All admin surfaces are gated by `getActiveAdminSession()` and support Light/Dark/System theming (`localStorage`-backed) per CLAUDE.md's color-token table. Settings (`/admin/settings`) has three tabs: My Account (change-password, theme toggle), Admin Users (list + Deactivate/Reactivate), and Activity Log (paginated, read-only view of `AdminActivityLog`, no filter UI yet). A shared `Modal` component supports `variant: 'brand' | 'neutral'`; `ConfirmModal.tsx` backs every admin confirmation dialog (no `window.confirm`/`window.alert` remains). Not built: additional admin roles, an "add new admin" UI, Activity Log filter UI.
- **Loading indicators**: A shared `src/components/ui/LoadingOverlay.tsx` (full-screen spinner overlay, `z-[100]`) is the standard way to show an in-flight submit/redirect state on all customer-facing buttons — buttons keep a permanent static label (still `disabled` while loading) instead of swapping their own text. The admin panel is not yet wired (separate follow-up, see Next Up).
- **Admin activity log**: `AdminActivityLog` (immutable, `createdAt`-only) plus `AdminActivityAction`/`AdminActivityEntityType` enums and `src/lib/admin-activity-log.ts`'s `logAdminActivity()` helper. Membership application approve/reject and booking reschedule each write a log row atomically alongside their real mutation; the renewal-link route writes one standalone per send/resend. `/admin/settings`'s Activity Log tab (`ActivityLogTab.tsx`, backed by `GET /api/admin/activity-log`) is a paginated (20/page, most-recent-first), read-only table — no filter UI yet.
- **Known dev-environment quirks** (mirrors CLAUDE.md's own Known Issues): `middleware.ts` does not execute locally (Next 16/Turbopack/Windows) — every gated route has its own working `auth()` check doing the real enforcement; re-verify against `staging` before assuming this is dev-only. The Browser pane doesn't composite frames in this environment — prefer DOM/class-based checks over `getComputedStyle`/screenshots for VERIFY.
